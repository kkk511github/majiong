# 按桌版本升级

## 边界

- 使用稳定HTTP/WebSocket入口和共享SQLite上的版本工作进程。前门不做牌局计算，服务器仍校验所有身份、权限、版本和动作revision。
- `playing`、`claiming`、`ended`属于正在进行的一整桌，激活新版本不会转移这些桌；新桌及尚未开局的等待桌归新版本。重连先按认证账号已入座的桌查归属，不接受客户端伪造座位来选择版本。
- 首次从原单进程系统启用必须使用安全窗口。原来不懂归属协议的进程不能与新工作进程同时写库。
- 初始bootstrap会暂缓新开局，保留准备状态；健康/源码/数据核验后显式activate才允许新开局。后续正常激活新版本不暂停旧对局。
- 稳定入口本身升级仍需要维护计划；不是所有基础设施变更都能无感。

## 工作进程

运行原`server/index.ts`，增加以下配置：

```
DATABASE_PATH=/app/data/mahjong.sqlite
MAHJONG_RUNTIME_ID=<每次发行唯一的节点ID，仅字母数字横线下划线>
MAHJONG_RUNTIME_RELEASE=<不可变发行标识>
MAHJONG_RUNTIME_ENDPOINT=http://<私有网络服务名>:8787
MAHJONG_RUNTIME_BOOTSTRAP=1 # 仅首次安全初始化，其他候选不设置
```

生产启动校验`release-manifest.json`发行标识及源文件哈希；不能把修改后的代码继续标成旧版本。lease及boot_id阻止双写，SQLite房间写入触发器还会拒绝没有注册写入身份的旧进程。已收桌保留路由墓碑，防止旧缓存复活牌桌。

前门运行`npm run server:gateway`，提供DATABASE_PATH和PORT，后端仅使用私有网络，不能对外开放绕过入口的端口。原反向代理仅指向稳定入口。现有账号、强更策略、牌桌权限、邀请与日志采集继续保留；强更保护覆盖所有版本的进行中桌。

## 后续发布

1. 验证候选镜像、源码清单及隔离测试，备份数据库和运行配置。
2. 使用新节点ID启动候选，绝不就地替换仍持有对局的旧节点。
3. `DATABASE_PATH=... npm run runtime:rollout -- status`只读查看归属。
4. `DATABASE_PATH=... npm run runtime:rollout -- activate <候选ID>`校验健康、发行和协议后原子切换新桌入口。
5. 旧桌继续打完；`retire <旧ID>`在还有playing/claiming/ended时会拒绝。完成后将等待/已结束展示状态交给新节点，fence旧节点，再停止对应旧容器。

## 回退与数据

- 不通过回滚数据库来回退已接受的新对局，也不强制收桌或踢人。
- 激活后若新节点已有对局，必须保留其原版本完成或原版本恢复，不能把这些桌随意交给旧引擎。
- 首次bootstrap尚未开放开局时，回退也要先确认没有进行中桌，再停止版本进程；解除运行归属机制属于显式运维操作，不能仅换回旧镜像。
- 提供`runtime:rollout -- abort-bootstrap`：仅在`accepting=0`、全部租约已结束、数据库内没有`playing/claiming/ended`时撤销路由表和房间写保护。它不恢复数据库，不删除账户、房间、账单、回放或强更政策。若进程被强杀，必须等原30秒租约自然到期，不得手工清租约绕过保护。
- 历史账单、已发送Telegram任务和强更设置不自动改写。回放先持久化为旧版本也能读取的gzip level0，后台完成压缩；崩溃、重启、清理期间不能丢失或复活回放。

## 生产接入与后续操作约束

- 首次接入以原有效Compose配置生成`compose.runtime.json`，保留数据库卷、密钥挂载、已有网络和公共`mahjong`别名；私有工作进程不继承公共别名，不发布宿主端口。生成器为`scripts/runtime-compose.mjs`，含结构验证测试。
- `server-mahjong-1`作为稳定前门，初始工作进程为`server-mahjong-blue-1`。原Caddy仍指向同一个`mahjong:8787`地址。Telegram和安装包服务不随引擎发布重启。
- 生产`.env`的`COMPOSE_FILE`选择运行时配置。**后续不能继续执行旧的“修改MAHJONG_RELEASE并重建mahjong”单服务发布脚本**；那会重建稳定前门，而不是发布候选引擎。
- 引擎及前门均直接执行`node --import tsx ...`，配合Compose的`init: true`传递停止信号。不要用无法可靠转发SIGTERM的npm包装进程替换该命令。
- 后续候选必须使用未占用的服务名、唯一运行节点ID和不可变镜像；从现有私有工作进程配置复制卷/网络，去除`MAHJONG_RUNTIME_BOOTSTRAP`，更新ID、release和指向自身服务名的endpoint。启动时只指定该候选服务，使用`--no-deps`，不得重建现存前门或旧工作进程。
- 健康、源码哈希和隔离测试通过后，调用`activate 新ID`。回退新桌准入可调用`activate 仍健康的旧ID`，但新版本已经开局的桌仍留在新版本，不能随准入回退被迁走。
- `retire 旧ID`成功后才停止旧容器。等待退役时把`ended`也算在进行中，不得把“本把结束”误当“整桌结束”。不要回收其镜像或把其节点ID复用于别的版本。
- 只支持向后兼容的共享数据库/协议变更。数据库破坏性迁移、稳定前门升级、证书/网关维护仍要单独制定维护方案，不能声称所有更新都无感。
- 原`0.8.5-hardening-20260927`不直接作为双版本参与节点：其延迟写事务在跨进程演练中曾产生断线保存锁冲突。首次启用会停止原单服务，再启动包含`BEGIN IMMEDIATE`并发适配的初始引擎；此后的候选也必须保留这项适配。实验中的`runtime-baseline`只给原镜像补齐并发事务，不改变玩法计分，用于验证不同发行镜像共存。

## 验证

隔离测试使用两个实际服务实例、真实认证会话和稳定入口，覆盖旧桌出牌、激活后新开局、旧桌重连、禁止提前退役及停止旧节点后新版连接继续工作。另有租约互斥、旧写入拒绝、不可变源码、邀请迁移、跨实例强更与回放持久化测试。线上切换前仍需独立核对活动桌与备份。

补充的`runtime-process.test.ts`启动三个独立Node进程，强杀旧引擎、等待真实租约过期后恢复，并验证重复杠牌请求不重复计分、候选桌在准入回退时保持归属、跨版本管理员操作以及会话撤销。写事务使用`BEGIN IMMEDIATE`，避免跨进程先读后写升级锁时的`SQLITE_BUSY_SNAPSHOT`。

Docker演练使用不同发行镜像、`--internal`网络和只读备份出来的生产数据副本。合成账号/牌局只能在`/lab/mahjong.sqlite`且显式`ROLLOUT_LAB=1`时生成；不复用真实会员会话，不把演练数据库回写生产。历史账单和政策按原始rowid边界逐行指纹复核。
