## 已复现的提示持续时间

`network-feedback.ts` 会在 connected/ready 状态下因平滑 RTT ≥600ms、心跳超时后的观察期或最近心跳超过45秒，显示同一个“网络波动”横幅。横幅本身不改分、不宣布操作失败。

使用现有 `measuredResponse()` 和 `networkFeedback()` 做计算复现：200ms 正常样本后单次 4800ms，随后每10秒均200ms，平滑 RTT 依次为1350、1063、847、685、564ms。因此正常回复恢复后仍显示约40秒。这是代码复现，并非今天玩家的实测样本。超时后还需3次成功回复才能解除观察状态。

现有诊断只保留最近32个事件，网络警告/RTT没有作为独立事件保存，且纯网络波动不会自动上报。因此尚不能精确认定今天多位用户的共同原因。需要对应会员与发生时间的诊断/复现进一步缩小范围。本次没有调整网络警告阈值、心跳超时或自动重发业务操作。

## Android 强制更新修复（本地代码，尚未打包发布）

原因为 `RequiredUpdate.tsx` 原先对所有原生平台直接调用 `openAppDistributionPage()`，未使用手动检查更新的下载逻辑。

- Android 最低版本拦截现在复用 `AppUpdate`，自动查询版本，用户点击“下载并更新”后走现有原生下载、SHA/包名/签名/Build核验和系统安装流程，不打开浏览器。
- 展示下载进度、取消、错误重试、未知来源安装权限和再次打开安装；关闭/Esc/安装返回不解除最低版本拦截。不把打开安装器视为安装成功。
- 查询与真正安装前均核对安装包版本不低于服务端要求；缺少有效包或包未达标时显示原因并允许重试，不跳网页，不降级。
- iOS 和网页版保留原路径。规则、算分、服务器最低版本策略没有变更。
- 老 APK 不会因服务端部署自动获得这个 UI 修改，需把修改打入后续 APK。此次没有生成安装包、发布更新或 push。
