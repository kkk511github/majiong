新增 [自动版本对照脚本](../../scripts/check-gameplay-compatibility.ts)，使用相同牌墙、操作序列和服务器时间，分别覆盖休闲、进园子、敞开头、进园子 B档，以及陪练和托管两种操作策略。每一步比较合法动作、四家的可见快照、完整实时状态、分数、逐笔流水和最新回放帧；每把结束比较所有历史及完整回放，再比较结算行。

| 原网络分支 `8779f08` | 32 桌、237 把 | 15466 次 | 61864 次 | 全部相同 |

原始结果见 [优化前版本对照](20261003-gameplay-baseline-compatibility.json) 和 [原网络分支对照](20261003-gameplay-network-compatibility.json)。两轮使用部分相同的种子，表中数字是实际执行次数，不代表 96 个互不重叠的随机样本。两轮报告记录了当前业务源码的 SHA256，便于确认报告对应哪一份尚未提交的代码。

每轮还比较 50 个已结算的桌外承包、清一色、全求人、抢杠、多人胡及连续下一把场景，包含倍率 1 和 2、不同付款余额；另确认 12 个零余额付款人禁止点炮或抢杠胡的场景仍不产生结算。每轮对 208 个战绩返回结果做完整对照，覆盖整桌与分局、日期总分、分页、会员查询、隐私、明细和旧记录的缺失基数及记分除数 1、2、5。比较未归一化分数、顺序、分页或权限，仅归一化已读时间戳是否存在。

服务端受理规则新增了重复、旧局和过期请求校验：重复请求确认原结果，已过期或跨局请求拒绝并同步状态。原分支的无加时请求曾可能在到期后、下一次 tick 扫描前受理；新代码按原有到期时间拒绝，未修改服务器规定的时间。累计 90 秒加时依然有效。本轮新增真实 Socket 测试确认额度剩余 1 ms 时仍可操作，到期和超出 1 ms 时拒绝；重复 ACK 不会再次扣时间。带新 revision 上下文的同时胡牌仍等待其他可胡玩家、保留一炮多响，并拒绝结算后的迟到杠牌。

打牌算分核对阶段重跑 545 项重点测试全部通过：规则、算分、回放和战绩 22 个文件 458 项，网络受理、时限、回执、状态复制及战绩优化 6 个文件 87 项。结果见 [规则与金额回归](../../test-results/gameplay-rules-recheck-20261003.json) 和 [网络与合法操作边界回归](../../test-results/gameplay-network-recheck-20261003.json)。TypeScript 和差异空白检查通过。该阶段只补检查脚本、测试、发布检查命令和报告，没有继续改动业务逻辑；后续 App 优化见下节，未改动玩法和算分。

## App 操作流畅度优化

此前已有牌桌模型复用、选牌回位过渡和跨 iframe 状态去重，见 [此前牌桌输入优化](../table-input-performance-20260926.md)。本次保留这些行为，继续减少 React 到 Cocos 通道中的重复计算和布局工作，不调整选牌、拖牌、碰杠胡或计分规则，也没有改变 Cocos 动画时长或美术资源。

| 本次发现 | 修改 | 保持不变的行为 |
| --- | --- | --- |
| 同一手牌收到 revision、在线状态、分数等新快照就重新计算可听弃牌；点选时还会重复算同一听口 | App 私有的单手牌缓存，让可听箭头和选牌预览共享原听牌函数的结果 | 本人手牌、花、副露来源和杠标志、规则、地胡听口、本人座位及公开碰牌变化时立即失效；按实体牌分别缓存，不读对手暗手 |
| RTT 采样或通知变化会重新构造整桌数组，导致尺寸观察器拆除重建和额外样式提交 | 显式记忆牌桌投影及倒计时状态；网络标签仍单独更新 | 连接、提交状态、暂停、选牌、真实快照和动作反馈变化仍及时传递；服务器仍确认操作结果 |
| 操作按钮位置每次固定搜索 500 个候选，即使第一项已是最优解 | 保持候选顺序和同分规则，跳过无法优于已有位置的候选；零代价合法位置直接返回 | 864 个屏幕尺寸、安全区、选牌、动作组合和密集牌桌场景的布局序列化结果与原算法一致，最小点击区域仍为 44 px |

缓存仅保留当前手牌及至多手牌张数加一的结果，换桌、换局、换座或离桌会清理；返回数组复制，调用方不能污染后续提示。公开未见张数没有缓存，对手弃牌或亮杠仍立即更新。开门花数门槛、压绝和地胡变化均有专门失效测试，四档规则的真实发牌和机器人动作还逐状态比较缓存前后的听口、可听弃牌及输入不变性。

## 数据库副本预检

新增 `npm run check:records-upgrade`。使用支持 `node:sqlite` 的 `backup` API 的 Node 运行时，本次验证为 Node 24.19.0。输入必须是已取得的数据库快照，输出目录必须不存在：

```bash
npm run check:records-upgrade -- \
  --snapshot /absolute/path/backup.sqlite \
  --output output/records-upgrade-rehearsal \
  --max-ms 5000 \
  --max-added-bytes 268435456
```

工具只读打开输入，用 SQLite 备份 API 包含尚未 checkpoint 的 WAL 内容，随后所有更改都在私有副本中执行。它强制演练首次参与者回填、双向比较派生索引与原记录、核对其他业务表指纹不变、检查数据库完整性和重复启动，并保存 `report.json`。超出耗时或空间门槛返回非零状态；已有输出不会被覆盖。

副本目录权限为 0700，数据库和报告为 0600。即使报告不包含凭证，副本仍包含账户、会话、回放等敏感数据，不能上传到公共仓库、当作上线数据库或回写生产。空间指标是已分配页数的增长，复用空闲页时可能为零，并不表示索引没有占用空间；还要预留备份、WAL 和运行余量。

本次只对合成 UI 数据库演练：2 桌、8 把、40 个派生参与者行，完整性、原表指纹和重复启动通过。单元测试另覆盖未 checkpoint 的 WAL、预算失败和禁止覆盖。**没有取得或测试生产数据副本**，小样本耗时不能用于批准生产维护窗口。

默认 100000 行是防止无意大批回填的保护阈值，不是耗时承诺。生产副本通过后，在维护窗口按实际规模显式核准 `MAHJONG_RECORD_INDEX_MAX_BACKFILL_ROWS`；不能为了让候选启动而盲目调大。首次升级仍可能持有写锁，进行中旧桌的写入会受影响，不应宣传成无感迁移。此工具仅演练参与者索引，不替代完整服务启动及其他索引的生产规模演练。

## 仍然存在的边界

命令回执仍是有容量的房间记录和近期缓存，不是永久的全局 exactly-once 账本。新客户端继续遵守“结果未知先同步，不自动重发”；有回执则确认原结果，回执不在但状态已变化则拒绝旧意图并同步，而不是伪装成功。离桌后跨进程重启不保证永久返回同一 ACK，但旧上下文不能作用于新桌。旧客户端没有新 revision 上下文，数字 requestId 仍只能连接内去重，不能声称只部署服务端就获得全部保护。

这些边界通过协议兼容、状态校验、明确失败和发布验收控制。本次没有引入跨服务全局账本、破坏性数据迁移或新的玩法结算协议。
