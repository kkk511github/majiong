# 战队定时统计

## 已确认的统计规则（2026-09-17 模板与最终战队）

单人练习不计入任何报表。客户端单人练习保存在设备本地的 `history:practice`，不上传服务器；报表查询另外排除 `code='练习桌'` 的记录，避免旧数据导入时混入。不要按玩家显示名或当前在线人数判断练习模式。

### 日清算

- 日结丁战队 + 日结冰战队合并成一份报表，每天北京时间 00:00 发送前一自然日的数据，首次计划为 2026-09-17 00:00。
- 同一会员在两队都有记录时，按用户 ID 汇总到一行；先合计分数，再除以 2。零分会员仍保留一行。
- 参考《每日日结人员（交）》：战队名、玩家ID、用户名、20分数、20金额、50分数、50积分、总结算。20 栏固定为 0；50积分 = 50分数 ÷ 2，总结算 = 20金额 + 50积分，保留正负和小数。
- 分数取原始逐把桌内加桌外输赢，并在每人每桌的首条已完成把数记录加上 `initialScore - settlementBase`（通常 90 − 100 = −10 桌费）。首条记录在日期和战队筛选前确定，跨日或换队不会重复扣费。缺少旧基线的记录不推测桌费。
- 按整桌结束时间 `match_records.at` 统计 `[开始,结束)` 内的已结束牌桌，整桌所有有效逐把流水一次归入该日期，跨零点不拆桌。未结束牌桌、未完成任何有效把的解散桌不计分；原始逐把流水不改写。成员本期全部记录按截止时最终战队汇总。
- 始终将上述原始净分数除以 2；不将 App 已折算的积分再除一次，不套用各牌桌的 `scoreDivisor`。
- 例：一名成员逐把净赢 70，扣一次桌费 10，分数 60，日清算积分 30。
- 文件名使用统计日：`日结算表2026.9.16.xlsx`，表内首行同样显示日期。

### 周结算

- 每隔完整 7 天发送三份报表：一生所爱战队单独一份，日结丁战队单独一份，冰茉莉战队 + 日结冰战队合并一份。从 2026-09-16 00:00 开始统计，首次发送为 2026-09-23 00:00。
- 参考《一生所爱工资总表8.31-9.6》：战队名、玩家ID、用户名、20金额、50局数、50积分、总结算。20金额固定为 0；每人每张实际已结束的牌桌计 1 局，50积分 = 50局数 × 3，总结算 = 20金额 + 50积分。示例牌桌完成 5 把仍计 1 局、3 分。合并组中同一会员汇总到一行，每张实际牌桌只计一次。
- 以整桌结束时间 `match_records.at` 归属周期，范围为 `[开始,结束)`。正在进行的牌桌、没有完成任何一把的解散桌不计局数。
- 成员本期所有已结束牌桌统一归到截止时最终战队。即使此前在其他队打牌，也只出现在最终战队所属的周表中。
- 文件名末日包含在统计范围内，例如 `冰茉莉战队+日结冰战队工资总表2026.9.16-9.22.xlsx`，实际查询截止 9 月 23 日 00:00（不含），完整覆盖 16–22 日。表内同样显示日期，跨年末日带年份。

### 最终战队

- 截止时间不含结束时刻。优先使用截止前的 `team_memberships` 归属；若其更新时间已经过了截止点，从 `account_audit` 的 `membership-changed` 事件恢复截止前最后一次归属（同毫秒按 rowid 顺序）。因此延迟生成不会把截止后的换队算进上一期。
- 明确退出战队、截止前尚未归队的成员不计入任何战队表；不以逐把旧战队替代最终战队。参赛禁用不抹去已完成记录。
- 日结和周结各自使用本期截止时间，跨队全期归集；重复发送重试使用首次生成的完整文件快照。

### 文件与发送

- ID 为麻将系统公开会员 ID（文本类型），用户名为登录账号，始终作为文字写入。文件为 `.xlsx`，保留模板列与计算公式；新增第一列战队名，首行为标题日期、第二行为表头，并冻结前两行。
- 无数据也发送表头和“本期无结算记录”。每日一份日结算；每七天另发三份周结算，在周结算日零点共四份。
- 所有日结、周结表最下方都有“总计”行，各数值列使用 SUM 汇总明细，保留正负和小数；空表总计为 0。总计行不包含在筛选范围内。
- 每份报表有独立的组 ID 和发送状态。同一战队可分别出现在日表和周表中，同类报表不允许重复包含一个战队。

## 运行方式

`compose.telegram.yaml` 是独立服务，读取麻将数据库的只读挂载，不重启游戏容器。发送状态和每次报表内容保存在独立持久卷。机器人 token 仅通过凭据文件挂载，不进入 Git、镜像或日志。

必需环境变量：

- `TELEGRAM_REPORT_CONFIG`：群 ID、已核验群名、时区和四条发送计划的 JSON。每条计划包含独立 `id`、合并名称 `name`、战队列表 `teams: [{id,name}]`，以及 `kind: dailyScore`（1 天）或 `kind: weeklyTables`（7 天）、`days`、`firstEnd`。合并名称必须等于所含战队名称用 `+` 连接的结果，每个战队 ID 和名称均与真实数据库核验。`countUnit: completedTables` 只描述周结算的局数单位。
- `TELEGRAM_BOT_TOKEN_FILE`：只含 bot token 的凭据文件。
- `DATABASE_PATH`：麻将数据库只读路径。
- `TELEGRAM_REPORT_STATE`：报表任务 SQLite 路径。

`node --import tsx server/telegram-report-worker.ts check` 核验机器人、精确群 ID、群名和发送文件权限。

`run` 长期运行；`once` 处理已到期任务；`status` 查看任务状态；`preview SCHEDULE_ID START END DIRECTORY` 只导出指定组和周期，不发 Telegram。起止时间须包含 `+08:00`，避免误用服务器的 UTC 时区。

v1/v2 → v3 合并报表升级须先停止报表服务并备份配置与报表状态库；只有尚无正式排队/发送任务的旧库可自动迁移，已有任务则拒绝改写，需先核对历史。最初的手动接入测试收据独立保存，不计入正式任务。迁移及读取只使用报表自身状态库，麻将数据库保持只读。v3 任务保存完整战队分组快照，后续配置变更或移除报表组必须先核对发送记录。

v3 → v4 不改变计划配置和数据库结构。已发送的 CSV、消息 ID 和 SHA-256 原样保留；已保存但待重试的 CSV 仍发送原快照，新报表保存 XLSX 的 base64 快照和实际二进制 SHA-256。Excel 模板位于 `server/report-xlsx/templates`，独立锁定的 ExcelJS 运行依赖只安装到报表镜像；本地测试先运行 `npm ci --prefix server/report-xlsx --ignore-scripts`。

## 可靠性

成功发送后保存 Telegram 消息 ID 和文件 SHA-256。已发周期不重复发送，重启后逐期补发遗漏周期。Telegram 明确限流时按照 `retry_after` 重试，重试使用已保存的原文件。

Telegram `sendDocument` 没有幂等键：上传后连接中断或进程重启，可能出现文件已到群但回执丢失。因此这类任务记为 `uncertain`，不会盲目重发；需先核对群内文件再处理。群权限或目标不一致记为 `blocked`。两类状态会使容器健康检查异常，任务记录保留具体原因。不能把这些状态当作已经送达。

API 依据：[Telegram Bot API](https://core.telegram.org/bots/api#senddocument)。
